# Grammar reference

## Files

| Shipped grammar | Source | Purpose |
|---|---|---|
| `syntaxes/rego.tmLanguage.json` | `scripts/grammar/rego.js` | The Rego language (`source.rego`) |
| `syntaxes/rego.injection.yaml.json` | `scripts/grammar/injection-yaml.js` | Rego in YAML block scalars, injected into `source.yaml` (matches the key) |
| `syntaxes/rego.injection.yaml.line-start.json` | `scripts/grammar/injection-yaml-line-start.js` | Same, for the YAML grammar of VS Code 1.85 to 1.91 (matches from column 0) |
| `syntaxes/rego.injection.markdown.json` | `scripts/grammar/injection-markdown.js` | ```` ```rego ```` fences, injected into `text.html.markdown` |

The JSON files are **generated**: edit the sources, then run `npm run build:grammars`.
`npm run check:grammars` (run in CI) fails if they are out of date.

Built-in functions come from `scripts/grammar/opa-builtins.json`. It is generated by
`npm run update:builtins -- vX.Y.Z` from two files of that OPA release:
`capabilities/vX.Y.Z.json` (which built-ins exist) and `builtin_metadata.json` (their official categories).
CI compares the list with `opa capabilities --current` of the pinned OPA binary.

## Scopes of `source.rego`

### Declarations

| Element | Scope |
|---|---|
| `package` | `keyword.control.package.rego` |
| package path (`a.b["c-d"]`) | `entity.name.namespace.rego` |
| `import` | `keyword.control.import.rego` |
| import path (`data.x`, `rego.v1`, `future.keywords.not`) | `entity.name.import.rego` |
| `as` / alias in an import | `keyword.control.as.rego` / `entity.name.alias.rego` |
| rule or function name in a rule head | `entity.name.function.rule.rego` |
| `default` | `keyword.control.rego` |

A rule head is only recognized at module level. Inside `{...}`, `[...]` and `(...)`, an identifier at the
start of a line is a local variable, an object key or an array item.

### Keywords and operators

| Element | Scope |
|---|---|
| `if` `else` `not` `with` `as` `default` `some` `every` `in` `contains` | `keyword.control.rego` |
| `and` `or` | `keyword.operator.logical.rego` |
| `:=` | `keyword.operator.assignment.rego` |
| `=` | `keyword.operator.unification.rego` |
| `==` `!=` `<` `>` `<=` `>=` | `keyword.operator.comparison.rego` |
| `+` `-` `*` `/` `%` | `keyword.operator.arithmetic.rego` |
| `&` `\|` (set intersection, union) | `keyword.operator.set.rego` |
| `\|` separating a comprehension's head from its body | `keyword.operator.comprehension.rego` |

Keywords are not highlighted after a dot: `input.in` or `x.contains` are plain ref segments
(OPA capability `keywords_in_refs`).

### Literals

| Element | Scope |
|---|---|
| `"..."` | `string.quoted.double.rego` |
| `` `...` `` | `string.quoted.raw.rego` |
| `$"..."` | `string.interpolated.rego` |
| `` $`...` `` | `string.interpolated.raw.rego` |
| `{expr}` inside a template string | `meta.template.expression.rego` (content `meta.embedded.line.rego`) |
| `\n` `\"` `\\` `\/` `\b` `\f` `\r` `\t` `\uXXXX`, and `\{` in template strings | `constant.character.escape.rego` |
| any other escape | `invalid.illegal.unrecognized-string-escape.rego` |
| `42` | `constant.numeric.integer.rego` |
| `3.14`, `1e10`, `2.5E-5` | `constant.numeric.float.rego` |
| `0x1F`, `0a2b` | `invalid.illegal.numeric.rego` |
| `true` `false` | `constant.language.boolean.rego` |
| `null` | `constant.language.null.rego` |
| `set()` | `support.type.set.rego` |

A double-quoted string ends at the end of its line, like in the OPA scanner. Raw strings may span lines.

### Names

| Element | Scope |
|---|---|
| `input` | `variable.language.input.rego` |
| `data` | `variable.language.data.rego` |
| `_` | `variable.language.wildcard.rego` |
| built-in call `count(x)` | `support.function.<category>.rego` |
| deprecated built-in call `any(x)` | `invalid.deprecated.builtin.rego` |
| other call `f(x)`, `data.lib.f(x)` | `entity.name.function.call.rego` |

`<category>` is OPA's official category: `aggregates`, `array`, `bits`, `conversions`, `crypto`, `encoding`,
`glob`, `graph`, `graphql`, `http`, `net`, `numbers`, `object`, `opa`, `providers.aws`, `regex`, `rego`,
`semver`, `sets`, `strings`, `time`, `tokens`, `tokensign`, `tracing`, `types`, `units`, `uri`, `uuid`, or
`builtin` for the few built-ins without a category (such as `print`).

### Comments

| Element | Scope |
|---|---|
| `# ...` | `comment.line.number-sign.rego` |
| `# METADATA` block (from column 1 until the first non-comment line) | `comment.block.documentation.metadata.rego` |
| `METADATA` | `storage.type.metadata.rego` |
| YAML keys in the block (`title:`) | `entity.name.tag.metadata.rego` |

### Punctuation

`punctuation.section.{braces,brackets,parens}.{begin,end}.rego`, `punctuation.accessor.rego` (`.`),
`punctuation.separator.comma.rego`, `punctuation.separator.key-value.rego` (`:`),
`punctuation.terminator.statement.rego` (`;`).

## Embedded Rego

Embedded code is scoped `meta.embedded.block.rego`, which `package.json` maps to the `rego` language
(`embeddedLanguages`). Comment toggling and bracket matching therefore use Rego's language configuration
inside the block.

### YAML

VS Code has shipped two YAML grammars, and `engines.vscode` (1.85) covers both:

| VS Code | YAML grammar | How indentation is handled |
|---|---|---|
| 1.92 and later | [RedCMD/YAML-Syntax-Highlighter](https://github.com/RedCMD/YAML-Syntax-Highlighter) | each nesting level consumes its indentation with a `\G`-anchored `while` rule |
| 1.85 to 1.91 | [textmate/yaml.tmbundle](https://github.com/textmate/yaml.tmbundle) | nothing consumes indentation |

The injection therefore comes in two grammars:

- `rego.injection.yaml.json` (selector `L:source.yaml -string -comment -meta.embedded.block.rego`) matches the
  key itself. With the current grammar, `\G` sits on the key's column when a line reaches the injection, so the
  block continues with `while: (?:\G|^)(?=[ \t]+\S|[ \t]*$)`: blank lines and lines indented more than the key.
- `rego.injection.yaml.line-start.json` (same selector **without** `L:`) captures the indentation from column 0
  (`^([ \t]*)`) and continues while lines are indented more than that capture. Only the older grammar reaches
  it: with the current one, indentation is consumed before injections are tried, so `^` cannot match.

The missing `L:` is deliberate. [vscode-textmate](https://github.com/microsoft/vscode-textmate) gives a tie
(same start position) to an injection only when its selector starts with `L:`. In the older grammar, the content
of another block scalar (`description: |` followed by `  rego: |`) starts a `string.unquoted.block.yaml` region at
column 0, and that region must win.

For the same reason, the line-start anchors of the Rego grammar are written `(?:^|\G)`.

### Markdown

The fence rules copy those that VS Code's Markdown grammar uses for its built-in languages
(`fenced_code_block_css`, ...). Behaviour is therefore identical: ```` ``` ```` or `~~~`, indentation, info-string
attributes, lists and block quotes.

## Testing

| Command | What it checks |
|---|---|
| `npm run test:grammar:rego` | `test/grammar/*.test.rego`: token-level assertions ([vscode-tmgrammar-test](https://github.com/PanAeon/vscode-tmgrammar-test) syntax) |
| `npm run test:grammar:embedded` | `test/embedded/*`: assertions on YAML and Markdown, using the VS Code grammars vendored in `test/vendor/vscode-grammars` |
| `npm run test:grammar:embedded:legacy` | the same YAML assertions with the YAML grammar of VS Code 1.85 (`test/vendor/vscode-1.85-grammars`) |
| `npm run test:unit` | Oniguruma compilation of every regex, includes, every built-in, fixtures never flagged invalid, snippets, manifest |
| `npm run test:integration` | Tokens computed by a real VS Code (`_workbench.captureSyntaxTokens`), snippet insertion, comment toggling |

`vscode-textmate` and `vscode-oniguruma` are pinned (npm `overrides`) to the versions shipped by VS Code.

In an assertion file, `#   ^^^ scope` checks the characters above the carets and `# <--- scope` checks from
column 0. A leading `-` lists the scopes that must be absent. To check where the carets point, run:

```bash
node scripts/show-assertion-targets.js test/grammar/literals.test.rego
```

To see the tokens of any file (after `npm run compile`):

```bash
node scripts/dump-tokens.js path/to/file.yaml
```

In VS Code, **Developer: Inspect Editor Tokens and Scopes** shows the scopes under the cursor.
